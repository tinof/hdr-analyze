# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

> Single source of truth for AI agents in this repo. `AGENTS.md` points here. Rust style and lint policy live in the "Lint/style policy" section below — there is no separate Rust guidelines pack.

## What this repo actually is

- Rust workspace (`resolver = "2"`) with **three shipped binaries**: `hdr_analyzer_mvp` (HDR10 analysis → PQ histograms + DV L1 metadata), `mkvdovi` (MKV container + Dolby Vision metadata injection, CM v4.0), `verifier` (MadVR / RPU measurement validation). A fourth workspace crate, `dovi84_composer`, is a library (no binary): the Profile 8.4 composers (`Composer::{Preset, Bt2100V1}`), their sidecar names and the RPU composer rewrite/check, shared by the analyzer and mkvdovi.
- `tools/compare_baseline`, `tools/l1_diff` and `tools/fit_hlg_composer` (fits the bt2100 composer constants in `dovi84_composer/src/bt2100_v1.rs`; also `rewrite-rpu <preset|bt2100> <RPU.bin>` for the validation scripts) are separate utility crates, **excluded** from the workspace. Build/run them explicitly with `--manifest-path tools/<name>/Cargo.toml`.
- Release profile is tuned: `lto = "fat"`, `codegen-units = 1`, `strip = true`, `panic = "abort"` — release builds are slow to link; expect it.

## Toolchain and platform quirks

- `rust-toolchain.toml` pins `channel = "stable"` (not a fixed version number) with components `clippy` + `rustfmt` and explicit cross targets. CI uses `dtolnay/rust-toolchain@stable`.
- `.cargo/config.toml` sets `build.rustflags = -C target-cpu=native`; on Linux ARM64 (`aarch64-unknown-linux-gnu`) it also sets `clang` + `lld`. Cargo does not merge the two: the target-specific `rustflags` replace `build.rustflags`, so on aarch64 `target-cpu=native` is **not** applied. Dev hosts: an Oracle ARM/Ampere box and an x86_64 WSL2 box with an RTX 4070 (the CUDA host). Don't remove either setting unless you mean to change perf/link behavior. `ci.yml` and `release.yml` set `RUSTFLAGS: ""`, which replaces `build.rustflags`: CI and release binaries target the baseline CPU, never the runner's. Keep that override — without it published binaries crash on other CPUs, and cached proc-macro libraries crash rustc on a runner with an older CPU.
- `ffmpeg-next` is used, so local/CI builds need FFmpeg dev libs + `clang`/`libclang` and `BINDGEN_EXTRA_CLANG_ARGS` configured — one composite action, `.github/actions/setup-ffmpeg`, does this per OS for both workflows (apt incl. `libclang-dev` on Linux, `brew install ffmpeg` on macOS, a checksum-verified BtbN LGPL shared build via `FFMPEG_DIR` on Windows). `ffmpeg-next` 9 is built with only `codec`/`format`/`software-scaling`, so avfilter/avdevice/swresample dev libs are not needed. The Windows release zip bundles the FFmpeg DLLs via `scripts/ci/bundle-windows-ffmpeg.sh`, which CI smoke-tests on every Windows build.

## High-signal commands (use these exact forms)

- Fast local quality gate (matches pre-commit + CI lint intent):
  - `cargo fmt --all -- --check`
  - `cargo clippy --workspace --all-targets -- -D warnings`
  - `cargo test --workspace --verbose`
- Build all release binaries: `cargo build --release --workspace`
- CUDA-enabled analyzer (NVIDIA hosts): `cargo build --release -p hdr_analyzer_mvp --features cuda` — also lint it with `cargo clippy -p hdr_analyzer_mvp --all-targets --features cuda -- -D warnings` (CI only covers the default feature set)
- Refresh the dev install after changes: `./scripts/dev-refresh.sh` — rebuilds the workspace release binaries **then**, when `nvidia-smi` is found (incl. the WSL path), the CUDA analyzer last (a plain workspace build overwrites the analyzer without the cuda feature). On this dev box `~/.local/bin/{mkvdovi,hdr_analyzer_mvp,verifier}` are symlinks into `target/release/`, so the system-wide commands always run the latest build.
- Test one crate: `cargo test -p hdr_analyzer_mvp` (or `-p mkvdovi`, `-p verifier`, `-p dovi84_composer`)
- Run a single test by name: `cargo test -p <crate> -- <test_name>`
- Run one binary: `cargo run -p <crate> -- ...`

## CI behavior that affects edits

- Job order in `.github/workflows/ci.yml`: **lint (fmt + clippy) → test → cross-platform build** (Ubuntu/macOS/Windows). Each later job `needs` the earlier ones.
- Security/dependency checks also run: `cargo audit`, and `cargo deny check` for `advisories` (allowed to fail, `continue-on-error`) and `bans licenses sources` (must pass). Exceptions live in `deny.toml` (incl. ignored `RUSTSEC-2025-0119` for `indicatif`, and `WTFPL` allowed for `ffmpeg-next`).
- Pre-commit hooks (`.pre-commit-config.yaml`): **on commit** = fmt check + clippy deny-warnings; **on push** = `cargo test --workspace -q`.

## Claude Code feedback loop (committed in `.claude/`)

- **Per edit:** rust-analyzer (the `rust-analyzer-lsp` plugin) pushes diagnostics after each Edit/Write, including `cargo check` flycheck results (type and borrow errors, tagged `(rustc)`). It needs the rustup component: `rustup component add rust-analyzer`. Without it, `~/.cargo/bin/rust-analyzer` is only the rustup proxy, the LSP server crashes with exit code 1, and no diagnostics arrive.
- **End of turn:** `.claude/hooks/rust-check.sh` (wired in `.claude/settings.json`). PostToolUse records touched `.rs`/Cargo/lint-config files. The Stop hook then rustfmts those files without reporting, and runs `cargo clippy --workspace --all-targets` (plus `--manifest-path tools/<crate>/Cargo.toml` for a touched tool crate). It feeds back only errors from any file and warnings in touched files. Turns without Rust edits never start cargo. After 3 feedback rounds it tells the user and stays quiet until the next Rust edit. State lives in `${TMPDIR:-/tmp}/claude-rust-check/<session_id>/`. An incremental run takes about 2–4 s on the `/mnt/c` checkout. Tests are not run here; they stay on pre-push.

## Roadmap workflow (committed in `.claude/`)

- **Cycle per roadmap step:** `/roadmap-next` (picks a step; Codex ranks independently as second advisor, the advisor tool reconciles) → plan mode (Codex plan-review hook) → implement → `/codex-ship`, whose step 1b runs `.claude/skills/pre-pr-review/SKILL.md` before the push, then the native Codex review, CI and merge. `/pre-pr-review` can also be typed alone.
- `/pre-pr-review` runs the saved workflow `.claude/workflows/pre-pr-panel.js` (three Opus review lenses, each finding checked by a skeptic). The workflow computes the **required gates** from the touched paths: analysis/decode/composer paths add `clippy-cuda` + `scripts/cuda-parity.sh`, analyzer/composer/`l1_diff` paths add the L1 regression gate, and build inputs (root `Cargo.toml`/`Cargo.lock`, the analyzer and composer manifests, `.cargo/config.toml`, `rust-toolchain.toml`) add both. A gate that cannot run, an unexpected `Skipping` line in the test log, or a lens that still returns nothing after one rerun (`complete: false`) blocks the push; findings whose verifier failed or that exceed the verify cap come back as `unverified` and are checked by hand.
- `.claude/agents/docs-keeper.md` updates the Markdown docs after the code fixes (ROADMAP item + log row, `docs/ROADMAP_LOG.md`, CHANGELOG `[Unreleased]`, CLAUDE.md, `docs/*.md`); it marks a step done only with acceptance-gate evidence. Steps that need the owner are listed under "Waiting for the owner" in `ROADMAP.md`.

## Real entrypoints and boundaries

- `hdr_analyzer_mvp/src/main.rs`: CLI parse + validation; orchestrates via `pipeline::run`. Core analysis lives in `analysis/` (frame, histogram, scene, hlg, gpu) plus `crop.rs`, `optimizer.rs`, `ffmpeg_io.rs`, `l1_sidecar.rs`, `writer.rs`. HLG is mapped to PQ through the Dolby Vision Profile 8.4 decode of the composer `--hlg-composer` selects (`analysis/hlg.rs`; `bt2100` = fitted to the BT.2100/BT.2408 1000-nit conversion, the default since 2026-10-03, design in `docs/HLG_COMPOSER.md`; `preset` = the `dolby_vision` crate's `Profile84` preset that `dovi_tool` writes; ignored for PQ): luma goes through the 8.4 luma reshaping curve (one 1024-entry LUT per composer, shared by CPU and GPU), and max-RGB (`Dovi84Decoder`, the HLG default like PQ) reconstructs the full decode per pixel (luma curve + the two order-3 chroma MMR curves + the RPU `ycc_to_rgb` matrix/offsets), then takes max(R′,G′,B′). Both are clamped to the RPU's source_min/max_pq [62, 3079] on purpose, so L1 stays in the declared range. Under the preset, neutral HLG reads about 2% higher in max-RGB than in luma (its chroma MMR tints neutrals slightly blue); bt2100 keeps neutrals neutral and holds neutral superwhite at 1000 nits. The first frame is always decoded, and a PQ/HLG tag on it overrides the stream tag; otherwise the stream tag is used (`ffmpeg_io::resolve_transfer`). That picks up HLG signalled via the alternative-transfer SEI (VUI says BT.2020) or only in the MKV Colour element. `--transfer auto|pq|hlg` overrides detection; mkvdovi always passes `--transfer hlg` for inputs MediaInfo classifies as HLG and hard-fails on an analyzer without the flag — a cross-binary contract like the `+cuda` probe; it always passes `--hlg-composer` for HLG when the analyzer's `--help` lists it (`external::analyzer_lists_option`); an analyzer without the option is accepted only for `--hlg-composer preset` (it measures through the preset), otherwise the file is refused. Input contract: only PQ/HLG transfers are analyzed (`TransferFunction::Unsupported` covers tagged SDR curves, incl. BT2020_10/12); samples are assumed limited-range BT.2020 NCL, with warnings for other range/matrix tags (BT.2020 CL included). mkvdovi refuses such HLG inputs instead (see the HLG → Profile 8.4 bullet).
- **Optional CUDA backend** (`cuda` cargo feature, off by default): `analysis/gpu.rs` + NVRTC-compiled `analysis/kernels.cu`. Activated at runtime by `--hwaccel cuda`; NVDEC decode via FFmpeg `AVHWDeviceContext` in `ffmpeg_io.rs` (cuvid → software fallbacks). Decoder and analyzer share device 0's **primary context** (`AV_CUDA_USE_PRIMARY_CONTEXT`; `GpuAnalyzer::new` sets `CU_CTX_SCHED_BLOCKING_SYNC` first, so it must stay ahead of `setup_hardware_decoder`), and P010 NVDEC frames are analyzed in place (`GpuAnalyzer::analyze_device`); `pipeline.rs` downloads a frame (`host_view`) only for fallback crop detection, scene-cut crop sampling or CPU analysis — never hand an `AV_PIX_FMT_CUDA` frame to host code. Frames also take the download path when the surface is not P010 (8/12-bit sources then fall back to CPU via the `gpu_failed` transition) or comes from another CUDA context (`hevc_cuvid`); a frame rejected before any CUDA work switches the run to the download path, but any failed CUDA call sets `GpuAnalyzer::context_faulted` and, with NVDEC frames, **stops the run** (the decoder shares the context, and FFmpeg's CUDA download can report success after a failed copy, so a download is no health check). Scene cuts download a frame only when crop monitoring is on (never with `--no-crop`). The crop probe decodes multithreaded and drains the decoder at EOF. `HDR_ANALYZER_CUDA_HOST_FRAMES` (any value) forces the download path for parity checks. Design, the optimization history and the rules for changing this path: `docs/CUDA_PIPELINE.md`. The kernel analyzes **full-resolution** frames with a sampling stride (`--downscale` = stride, no swscale), so its crop rect lives in full-res coordinates — `pipeline.rs` scales rects between spaces (`scale_rect`/`shrink_rect`). `--pre-denoise median3` is CPU-only. `--peak-estimator robust` runs in the kernel: it fills the cross-quad diff histogram (16x64 u32 after the u64 sums, `DIFF_WORD`) only when that estimator is selected (`grain_stats`), and the host applies the same `frame.rs` functions; with other estimators GPU `FramePeakStats` report neutral sigma/n_eff. The CPU computes the PQ max-RGB mix and the per-pixel PQ bin (`pixel_pq_bin`) in the kernel's f32 arithmetic, and the kernel uses `_rn` intrinsics there, so histograms and maxima are bit-identical; keep both sides operation for operation. Validated bit-identical L1 output vs. CPU (the HLG max-RGB decode too: f32, fixed op order, non-contracting `__fmul_rn`/`__fadd_rn`). Keep the kernel result-buffer layout (counts, then u64 sums at `SUMS_WORD`) and the `dovi_params` buffer layout (`DOVI_*` constants) in sync between `kernels.cu` and `gpu.rs`. Cross-thread reductions in the kernel must stay order-independent (integer counts, u64 fixed-point sums, max of non-negative f32 bits) so launch-shape changes stay bit-identical. Benchmark with `--no-crop` (or subtract the crop probe) and report frames ÷ wall time; `--profile-performance`'s "Analysis" fps excludes decode.
- `mkvdovi/src/main.rs`: file discovery/sorting + early `inspect` dispatch + per-file orchestration via `pipeline::convert_file`. Key modules: `rpu_check.rs` (MEL/FEL/P8 classification and RPU diagnostics; it is what detects FEL), `external.rs` (tool checks/invocation), `metadata.rs` (`CmV40Config`, L2/L5/L9/L11 generation), `verify.rs`, `progress.rs`.
- `verifier/src/main.rs`: standalone measurement-validator CLI.

## mkvdovi operational gotchas (easy to miss)

- **Checks external tools at runtime** (`external::check_dependencies`): requires `ffmpeg`, `mkvmerge`, `dovi_tool`, and either `mediainfo` or `ffprobe`. HDR10+ processing additionally invokes `hdr10plus_tool` — keep it in `PATH` for HDR10+ inputs.
- `dovi_tool` 2.3.2 is the floor (its `inject-rpu` padding fix is relied on by the existing orchestration call); 2.3.4+ lets mkvdovi pass the MKV directly to remove/convert/demux (`--dovi-input auto|raw|mkv`, auto = on when 2.3.4+ detected via `dovi_tool --version`), with automatic per-step fallback to ffmpeg extraction; direct attempts log to `*_mkv.log` in the temp dir.
- `dovi_tool` 2.3.4 parses Level 253 ext-metadata blocks, but the `dolby_vision` crate 3.4.0 used in-process (inspect sampling, MEL/FEL classification) does not yet — re-bump when the crate releases L253 support.
- With no input args, it recursively processes `.mkv` files from cwd, skipping `mkvdovi_temp_*`/legacy `mkvdolby_temp_*` paths and files already ending `.DV.mkv`. Explicit `--mdfix` allows a DV input and writes a distinct `*.mdfix.DV.mkv` candidate.
- **Successful conversion deletes the source input by default**; pass `--keep-source` to prevent deletion.
- **Robust to interruption:** extract/inject/mux show a live byte-progress bar (throughput + ETA) and warn after `--stall-timeout` (default 300s, `0` disables) if the output file stops growing. An interrupted run (e.g. SSH `SIGHUP`) preserves `mkvdovi_temp_*` and prints a resume hint; a re-run **auto-resumes** by reusing completed steps, gated by `<artifact>.done` sentinels plus a `resume.json` fingerprint (input name/size/mtime, mkvdovi version, artifact-affecting settings from `pipeline::resume_settings`); a temp dir with a different fingerprint is discarded, while one with no fingerprint (older mkvdovi, legacy `mkvdolby_temp_*`) resumes with a warning (`resume.rs`), except under a non-preset `--hlg-composer`, where it is discarded. A non-preset HLG composer adds ` hlg_composer=<luminance_mapping>` to the settings string (only then, so default fingerprints are unchanged). Add any new artifact-affecting flag to `resume_settings`. The fingerprint does not cover the measurements: `convert_file` compares the regenerated `extra.json` with the one in the temp dir and withdraws the `RPU.bin`/`BL_RPU.hevc` sentinels (`resume::invalidate`) and the `mux.done` marker when they differ, so a re-analysis is never paired with a stale RPU. `--no-resume` forces a clean run. Run long conversions under `tmux`/`nohup`.
- For HDR10 without **valid** measurements, it auto-runs `hdr_analyzer_mvp`: every existing measurements candidate is tried in turn (the analyzer's own `<stem>_measurements.bin` first, a shared `measurements.bin` last), and the first whose `.l1.json` sidecar validates against the input (name, size, contiguous scenes, MediaInfo frame count within `metadata::frame_count_tolerance`, because MediaInfo estimates counts from duration for untagged MKVs) is reused; otherwise analysis re-runs. Scenes outside min <= avg <= max are a warning, not a rejection: `--peak-domain luma` and percentile/robust estimators legitimately produce them. `--legacy-madvr-l1` is the only way to reach the old `--madvr-file --use-custom-targets` L1 (optimizer targets as max, placeholder avg); it is HDR10-only and refused for HLG. `--analysis-quality` controls sampling (downscale/sample-rate): `auto` (default) = `accurate` when GPU analysis is available else `balanced`; `fast` = half-res/every 3rd frame, `balanced` = half-res/every frame, `accurate` = full-res/every frame.
- **L1 sidecar contract:** the analyzer writes per-scene L1 stats to `<measurements>.l1.json` (`hdr_analyzer_mvp/src/l1_sidecar.rs`); mkvdovi reads it via `metadata::load_l1_sidecar` for source-honest per-scene L1. The analyzer writes `version: 5` (v2 added provenance + full-resolution `crop`, which mkvdovi turns into L5 offsets; v3 added `analysis.luminance_mapping`: `pq`, or for HLG the composer's name from `Composer::luminance_mapping`: `dovi84-v2` (preset, full 8.4 decode) or `dovi84-bt2100-v1`; the older luma-only `dovi84-v1` came from pre-release builds); v4 has the same layout but stores **unfiltered** frame/scene averages (`FrameL1Measurement::avg_luma_pq`/`avg_max_rgb_pq`; only `MadVRFrame::avg_pq` in the `.bin` still goes through the histogram EMA); v4 max-RGB runs also carry an optional `light_level` block (MaxCLL/MaxFALL in nits over the crop, FALL as a linear-light mean of the 4096-bin PQ histogram), which mkvdovi uses for L6 fields the source does not state (`metadata::resolve_light_levels`: needs `sample_rate` 1, and `downscale` 1 for MaxCLL; never changes a source-stated value; HLG MaxCLL is capped at 1000); v5 adds `source.stream_frames` and `source.leading_skipped_frames`. An open-GOP cut at a CRA starts with RASL pictures no decoder outputs, but `dovi_tool inject-rpu` maps RPU `n` to presentation picture `n` and those pictures come first. So the analyzer counts them from the packets' NAL types (`leading_pictures.rs`) and fails on any other difference between decoded frames and pictures (packets that carry a slice) (`pipeline::account_stream_frames`). `metadata::generate_extra_json` shifts the shots by the count (`L1Sidecar::stream_frame_count` = RPU length), and `verify.rs` compares in stream frames. A pre-v5 sidecar is reused only on an exact MediaInfo frame count. Inject output containing "mismatched lengths" is a hard failure for a measured RPU. mkvdovi and `tools/l1_diff` accept 1–5 (`metadata::L1_SIDECAR_MAX_VERSION`), and mkvdovi reuses a pre-v4 sidecar with an advisory about smoothed averages, and HLG inputs require v3 or later + exactly the selected composer's name (`metadata::check_luminance_mapping`; a sidecar of the other composer, an unknown `dovi84-*` name or luma-only `dovi84-v1` is re-analyzed with a visible message; adding `dovi84-v2` kept version 3, and `dovi84-bt2100-v1` kept version 4, because each is a new value of an existing field). A missing/invalid/unknown-version sidecar produces a visible warning and re-analysis, never a silent fallback — a schema change must still bump the version on both sides (same class of cross-binary contract as the `+cuda` version probe).
- `--hwaccel` defaults to **`auto`**: `pipeline::resolve_auto_settings` (called once from `main.rs`) probes `nvidia-smi` (incl. `/usr/lib/wsl/lib/nvidia-smi` on WSL2) and resolves to `cuda` or `none` before any file processing — downstream code only ever sees concrete values. GPU analysis availability is probed via `hdr_analyzer_mvp --version` containing `+cuda` (set from the analyzer's `cuda` feature in its `cli.rs` VERSION const — keep that contract if you touch either side). `--hwaccel` only selects GPU decode + analysis in the analyzer; it never selects an encoder.
- Explicit `mkvdovi --hwaccel cuda` is forwarded to the spawned `hdr_analyzer_mvp` (GPU analysis if that binary was built with `--features cuda`). mkvdovi finds the analyzer in this order (`pipeline::analyzer_executable`): next to the mkvdovi executable, then `target/release/hdr_analyzer_mvp` relative to cwd, then PATH.
- **External tool runners (`external.rs`):** `run_command`/`run_command_with_spinner` must leave the child's pipes attached and let `wait_with_output` drain them; taking `child.stdout`/`stderr` out first deadlocks once a tool writes >64 KB (this hung `--verify` on a 1,263-scene episode until 0.5.1). Long-running steps use `run_command_with_progress`/`run_command_live`, which drain on threads.
- For HDR10+ input, L1 is derived from source HDR10+ metadata; panel peak is **not** passed as a `--trim-targets` override. HDR10+ scene peaks above 3× mastering-display peak produce advisory warnings only — **never add a silent clamp**.
- `--verify` resolves tools from `PATH`, validates structured RPU frame JSON, and hard-fails malformed Profile 8 / L1 / L6 / CM v4.0 L9/L11/L254 metadata, or an RPU frame count that differs from the muxed video track (MediaInfo `FrameCount`) or the L1 sidecar. For HLG output it also hard-fails when there are no measurements or the sidecar does not load, and checks that **every** RPU frame carries the composer the sidecar names (`dovi84_composer::check_rpu_file`). For a generated RPU (`verify::DeliveryExpectation`; not the MEL passthrough, whose RPU can carry levels the crate cannot parse, such as L253) it parses the extracted RPU in-process (frame count from the parse) and hard-fails a frame whose source range differs from `metadata::expected_source_range`, or whose L1 differs from the sidecar scene's L1 after the generator's clamp (`ExtMetadataBlockLevel1::from_stats_cm_version(.., V29)`). The clamps themselves are only reported. The pipeline passes no sidecar for HDR10+ and under `--legacy-madvr-l1`, because then the RPU's L1 does not come from it.
- `scripts/mkvdovi_hifi_workflow.sh` is a specialist comparison helper for inputs that **already** contain DV metadata. Use `mkvdovi` directly for HDR10+ sources.
- `inspect` dispatches before dependency checks.
- **HLG → Profile 8.4, no re-encode:** the HLG stream is copied bit-exact and gets an 8.4 RPU (`metadata::dv_profile_for`); L1 comes from the analyzer's 8.4-decode measurement through the selected composer. `--hlg-composer bt2100` is the default (switched by owner decision before the playback test; whether playback devices apply it is still unverified); `preset` keeps the RPU exactly as `dovi_tool generate` writes it and is the fallback. For bt2100, `generate_rpu` rewrites the composer with `dovi84_composer::rewrite_rpu_file` before the `RPU.bin` sentinel; the rewrite refuses an RPU whose frames do not carry the preset mapping or that does not round-trip byte for byte through the `dolby_vision` crate, and writes atomically. Every HLG input (any composer) tagged full range, with a matrix other than BT.2020 NCL (BT.2020 CL included) or primaries other than BT.2020 in MediaInfo or ffprobe is refused before any temp work (`metadata::check_hlg_colour_contract`); untagged fields pass with a warning. There is no HLG→PQ encode path any more. `--mdfix` on an 8.4 input is refused.
- **mkvdovi never encodes video:** every path copies the video stream bit-exactly. There is no compositor, no `composite-pipe`, no `--fel-*`/`--encoder` flag and no Modal/NVENC/libx265/VideoToolbox encode; do not add one back.
- **Profile 7 FEL is refused** (with or without `--mdfix`): a per-file hard error before any temp work, the source is never deleted, and a multi-file run continues with the next file. The BL+EL compositor was removed because it did not match ETSI GS CCM 001 on real discs (measured mean chroma error 69 to 534 10-bit codes on seven of eight FEL test cuts). The plan for FEL without a re-encode (base layer bit-exact, FEL information carried in the 8.1 RPU as far as possible) is `docs/FEL_PLAN.md`. `inspect` still reports FEL.
- Profile 7 MEL uses a fast metadata-only discard path unless `--mdfix` is requested. MEL/Profile 8 `--mdfix` rebuilds metadata from a clean base layer. All DV/repair inputs keep their source by default.
- `dovi_tool generate` clamps L1: min is written as at most 12 codes, max as at least 2081 (100 nits), and avg as at least 819, because mkvdovi sets `l1_avg_pq_cm_version: V29` under CM v4.0 too (`metadata::generate_extra_json`); a measured value outside those limits does not reach the RPU.
- mkvdovi passes `source_min_pq`/`source_max_pq` for 8.1 explicitly in `extra.json` (`metadata::source_range_pq_81`: `dolby_vision::utils::nits_to_pq_12_bit` of the mastering min/max, the crate's CM XML convention). Without them `dovi_tool generate` falls back to a coarse L6 lookup (mastering max other than 1000/2000/4000/10000 nits → 3079; mastering min other than ≤0.001 or exactly 0.005 nits → 0), which is still what happens for implausible mastering values (peak outside `MASTERING_PEAK_NITS` 100–10000, min outside `MASTERING_MIN_NITS` 0–1; warned, because a wrong-units SEI would otherwise set a 0.1-nit source range). Never pass them for 8.4: `change_source_levels` overrides on any value, and both HLG composers and the HLG measurement assume the preset's 62/3079 (`metadata::source_range_pq_84`).
- libplacebo (mpv, VLC, ffmpeg) reads only L1 max/avg and `source_min_pq`/`source_max_pq` from an RPU for display mapping, plus the reshaping/NLQ; it ignores L1 min, L2, L3, L5, L6, L8, L9 and L11, so a libplacebo render cannot test those levels.
- The `dolby_vision` crate (3.4.0) stores reshaping pivots delta-coded, as read from the bitstream; accumulate them before comparing with sample values.
- `--mdfix` regenerates the RPU with `dovi_tool generate`: authored L2 trims are replaced by neutral ones and authored L4 is dropped (the generator emits no L4).

### Generated DV metadata levels (mkvdovi, CM v4.0 by default)

- **L1** per-frame luminance (from HDR10+ or hdr_analyzer) · **L2** trims for 100/600/1000-nit targets · **L6** static mastering metadata (MaxCLL/MaxFALL) · **L9** source primaries (auto-detected) · **L11** content type + reference mode.
- Defaults: `--cm-version v40` (or `v29`); `--content-type movies` (default — valid: `default`, `movies`, `game`, `sport`, `user-generated-content`; `cinema`/`film` alias `movies`, `gaming` aliases `game`); `--reference-mode false`; `--source-primaries` auto (`0=P3-D65, 1=BT.709, 2=BT.2020`). `-v/--verbose` shows raw tool output; `-q/--quiet` minimal.
- Progress uses `indicatif` spinners with TTY detection (auto-disabled in CI/non-interactive).

## Testing quirks

- `mkvdovi` integration tests are environment-dependent: they **skip** when `dovi_tool` is not in `PATH`, and when the sample media file is absent (`../tests/hdr-media/...mkv`). `mkvdovi/tests/hlg_profile84.rs` also skips unless ffmpeg (with libx265), ffprobe, mkvmerge and dovi_tool are available, plus (except the colour-refusal tests) an `hdr_analyzer_mvp` built next to mkvdovi whose `--help` no longer lists the removed `--hlg-peak-nits`; its bt2100 test also skips when that analyzer's `--help` lacks `--hlg-composer`. `mkvdovi/tests/open_gop_start.rs` skips on the same tools, without a sibling analyzer, or when that analyzer writes a pre-v5 sidecar. `hdr_analyzer_mvp/tests/real_content_consistency.rs` skips without its media, and its reference-bias check without `HDR_ANALYZE_REFERENCE_CSV`/`HDR_ANALYZE_SHOTLIST`. Do not assume all workspace tests are hermetic on a clean machine.
- CI never exercises the CUDA path (no GPU runner). After a change to `analysis/`, `kernels.cu` or `ffmpeg_io.rs`, run `scripts/cuda-parity.sh` on a CUDA host: it generates PQ and HLG HEVC clips and runs `hdr_analyzer_mvp/tests/cuda_parity.rs` with `HDR_ANALYZE_CUDA_PARITY_REQUIRED` set (CPU vs CUDA `.bin` bytes and sidecar crop/scenes/frames, `gpu: true` asserted; without the env vars the test skips). The HLG clip runs once per composer in `HDR_ANALYZE_CUDA_PARITY_HLG_COMPOSERS` (the script sets `preset,bt2100`; unset = all), each asserting its `luminance_mapping`, and the PQ clip also runs with `--hlg-composer bt2100`, which must not change its `.bin`. For old-vs-new build comparisons the manual check in `docs/CUDA_PIPELINE.md` still applies.
- **L1 regression gate (CI job `l1-regression`):** `scripts/ci/l1-regression-gate.sh` scores the analyzer on the synthetic clip from `tools/l1_diff/corpus/make_corpus.py` against the committed `*.reference.csv` / `*.scenes.txt` with `l1_diff --max-*` limits. A change that moves L1 on purpose needs `--update` and the reference diff in the PR. The same job runs fmt/clippy/test for `tools/l1_diff` (outside the workspace). `scripts/rpu-baseline.sh capture|compare` does the equivalent for the final RPU of real media (baselines live outside the repo, e.g. `~/mkvdovi-work/rpu-baseline/<version>/`).
- **Real-content corpus (local only, never in the repository):** 45 development cuts under `~/mkvdovi-work/corpus/dev` (HDR10, HDR10+, HLG, Profile 7 MEL / 8.1 with retail L1, synthetic grain and highlight pairs) and 29 unanalyzed holdout cuts under `~/mkvdovi-work/corpus/qual/holdout`. Each development cut has `input.mkv`, `manifest.json`, `truth/` (retail L1, RPU, HDR10+ JSON, shot list; `truth/rejected/` holds metadata found not to describe the picture) and an accepted `baseline/`. The scoring script, its docs and all results live on the local-only branch `feat/dev-corpus` (`docs/VALIDATION.md` §10 there); a `.git/hooks/pre-push` guard refuses that branch and any push that adds its script name, so do not name the script in files on `main`. Dolby tool output only scores, never tunes; holdout cuts are not analyzed during development ([`docs/PROVENANCE.md`](docs/PROVENANCE.md)). Inventory and findings: [`docs/ROADMAP_LOG.md`](docs/ROADMAP_LOG.md) (2026-10-05).

## Lint/style policy in this repo (non-default)

- Workspace lints in root `Cargo.toml`: clippy `all` allowed but `correctness` denied; `dbg_macro` denied; rustc `rust_2018_idioms` and `unused_qualifications` warn — all of which fail under `-D warnings` in CI. `unwrap`/`expect`/`print` are allowed everywhere (the `allow-*-in-tests` keys in `clippy.toml` have no effect because those lints are never enabled).
- `unsafe_op_in_unsafe_fn = "deny"`, but `unsafe_code` is **allowed**.
- `clippy.toml` is tuned for this domain (higher complexity thresholds).
- Nothing lints the `cuda`-gated Rust code except a manual `cargo clippy -p hdr_analyzer_mvp --all-targets --features cuda -- -D warnings` (not CI, not the Stop hook), and `kernels.cu` is only compiled by NVRTC at runtime — a kernel error shows up only in a `--hwaccel cuda` run.
- CI runs on pushes to `main` and `fix-*` and on PRs to `main`; other branches (e.g. `perf/*`) get CI only through a PR.
- Imports: std → third-party → `crate::`, grouped with braces, absolute `crate::` paths internally. `anyhow::Result` + `.context()` at app level; `thiserror` for library error types.

## Releases

Bump version in each crate's `Cargo.toml`, add a `CHANGELOG.md` entry, then tag & push (`git tag vX.Y.Z && git push origin vX.Y.Z`). `release.yml` builds Windows x64, macOS Intel+ARM, and Linux x64, creates the GitHub release, and uploads archives with the three binaries + `README.md`/`LICENSE`/`CHANGELOG.md`. **Linux ARM64 is not automated** (runner limitation).

## Symbol navigation: LSP-first (rust-analyzer)

The native LSP tool (rust-analyzer plugin) is PRIMARY for symbol questions in this repo — not grep:

| Task | LSP operation |
|------|---------------|
| Who calls this / uses this field? | `findReferences` / `incomingCalls` |
| What does this function call? | `outgoingCalls` (resolves into deps too, not just this crate) |
| Where is this defined? | `goToDefinition` (or `workspaceSymbol` from a name) |
| What's the type/signature? | `hover` (returns the full signature **plus** the doc comment) |
| What's in this file? | `documentSymbol` |

- LSP is a deferred tool: load it early with `ToolSearch` query `select:LSP` (a SessionStart hook reminds you).
- **Warm the index first, and expect a wait.** One cheap `documentSymbol` call on an entrypoint (e.g. `hdr_analyzer_mvp/src/main.rs`) kicks off indexing, but it is not instant: on this host the first `workspaceSymbol` still returned empty and only resolved after ~45s. `documentSymbol` works immediately; treat an empty `workspaceSymbol` as "still indexing", not "no such symbol", and retry once.
- **Positions are 1-based on both axes and must land exactly on the symbol.** `goToImplementation` at `mkvdovi/src/progress.rs:127:11` (inside the `for` keyword) returned "no definition found"; the same call at `127:6` (on `Drop`) returned 182 impls. A "no definition found" result usually means a bad column, not a missing symbol — recount before concluding anything.
- **`goToImplementation` has little local value here: the repo declares no traits of its own** (`rg '^(pub )?trait '` → zero hits). Every `impl X for Y` implements a std or third-party trait, so the operation dumps the whole ecosystem's impl list (182 entries for `Drop`, of which 2 are ours). For repo-local work use `findReferences` and the call-hierarchy pair instead.
- Cross-crate and cross-dep resolution both work: `findReferences` on `l1_sidecar::write_l1_sidecar` finds its `pipeline.rs` call sites, and `outgoingCalls` resolves through to `anyhow::Context::with_context`, `serde_json::to_writer_pretty` and `std::fs::File::create`. `incomingCalls` also surfaces **test** callers, which is the cheapest way to find a function's existing coverage.
- **Review/audit/triage sweeps** ("find all X", "any stubs?") lead with `Grep` for exhaustive exact-pattern coverage (`todo!`, `unimplemented!`, `// TODO`, `// FIXME`), then read flagged bodies.
